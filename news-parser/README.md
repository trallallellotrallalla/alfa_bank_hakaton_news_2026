# news-parser — модуль сбора и индексации новостей

Модуль проекта «Новостная аналитика для принятия бизнес-решений» (Альфа Хак 2026).
Закрывает пункт 2 постановки: **парсер для сбора и обработки новостей из внешних
источников и аналитики Альфа-Банка, их классификация и выделение ключевой информации**.
Результат — база событий и фрагментов аналитики с метками и эмбеддингами, по которой
агент (другой модуль) делает RAG-поиск под профиль клиента.

Модуль не пишет интерпретации для клиента и не ранжирует ленту окончательно: это задача
агента. Модуль отвечает за то, чтобы агенту было из чего выбирать. Данные для этого
должны быть чистыми, без дублей, размеченными, с первоисточниками и с понятным
происхождением каждой метки.

## 1. Место в системе

```
   Источники                      news-parser (этот модуль)                    Другие модули
 ┌─────────────┐   ┌──────────────────────────────────────────────────┐
 │ RSS СМИ     │──▶│ коллекторы → очистка → дедуп → префильтр →       │
 │ ЦБ РФ       │──▶│ LLM-извлечение → эмбеддинг → склейка в события   │  функции /   ┌──────────┐
 │ MOEX ISS    │──▶│                                                  │◀────CLI─────▶│  Агент   │
 │ ручной ввод │──▶│ PDF аналитики Альфа-Банка → фрагменты → метки    │              └──────────┘
 └─────────────┘   └───────────────────────┬──────────────────────────┘
                                           │ схема news.*
                                   ┌───────▼────────┐
                                   │ PostgreSQL +   │
                                   │ pgvector       │
                                   └────────────────┘
```

- Модуль — **Python-библиотека + фоновый воркер**. HTTP-сервера нет: другие модули вызывают
  функции (`from news_parser import get_packets`) или CLI (`python -m news_parser.cli packets U_176`).
- В Docker работает **воркер**: собирает и обрабатывает новости по расписанию.
- Все его таблицы лежат в **отдельной схеме БД** `news`, поэтому общая база с другими
  модулями не конфликтует.
- Сбор идёт сам по расписанию внутри контейнера, внешний cron не нужен.
- Наружу модуль общается **только через функции `news_parser.interface`**. Агенту не нужно знать про таблицы,
  и эмбеддинги запросов он тоже не считает: текст запроса векторизуется внутри модуля
  той же моделью, что и документы.

## 2. Как это работает: пайплайн

Код пайплайна — `src/news_parser/parser/pipeline.py`. Каждый элемент обрабатывается
независимо: ошибка в одной статье не роняет весь сбор. Медленные шаги (сеть, LLM,
эмбеддинги) выполняются **вне транзакций БД**.

### Шаг 1. Сбор — `parser/collectors/`

Каждый тип источника — класс-коллектор с методом `collect()`, который возвращает
список «сырых» элементов `RawItem`. Источники перечислены в `config/sources.yaml`.

| Тип | Что делает | Источники по умолчанию |
|---|---|---|
| `rss` | читает RSS/Atom-ленту; полный текст берёт из ленты (РБК отдаёт его внутри) или скачивает по ссылке | РБК, Интерфакс, Коммерсантъ, Ведомости, ТАСС, пресс-релизы ЦБ |
| `cbr_fx` | официальные курсы ЦБ (USD/EUR/CNY), сравнение с прошлой датой | ЦБ РФ |
| `moex_index` | закрытия индексов (IMOEX, RGBI), сравнение с прошлым днём | MOEX ISS |
| ручной ввод | функция `ingest(url=… или title=…, text=…)` | — |

Структурированные источники (ЦБ, биржа) превращают цифры в событие **только при
существенном изменении** (`alert_threshold_pct`), иначе лента засорилась бы ежедневным
«курс почти не изменился». Разметку для них код знает заранее, LLM не вызывается.

### Шаг 2. Получение и очистка текста — `parser/cleaner.py`, `parser/fetcher.py`

- Если статья с таким URL уже есть в базе, она **пропускается до скачивания**
  (статус `known_url`), чтобы не качать одно и то же каждые 15 минут.
- Полный текст достаёт `trafilatura`: он убирает меню, рекламу и блоки «читайте также».
- Перед скачиванием проверяется **robots.txt**, между запросами к одному сайту
  выдерживается пауза (`HTTP_DELAY_S`).
- Если полный текст недоступен, используется анонс из RSS.

### Шаг 3. Точный дедуп — `cleaner.content_hash`

Хеш строится по тексту без регистра, пунктуации и лишних пробелов. Тот же текст у
другого источника получает статус `duplicate` и **привязывается к событию оригинала**
как ещё один источник. Модель на него не тратится.

### Шаг 4. Префильтр без LLM — `parser/prefilter.py`

Дешёвый отсев до LLM-классификатора, чтобы в LLM уходило как можно меньше статей.
Смотрит **только на текст публикации** (заголовок + тело). Мета (URL, источник, дата)
сюда не подаётся, как и в классификатор: она идёт сразу в БД.

Префильтр не решает, подходит ли новость конкретному клиенту (это правила на этапе
запроса). Он выкидывает то, что не нужно никому:

- слишком короткий текст → `filtered: too_short`;
- реклама (маркировка `erid`, «на правах рекламы», промокоды) → `filtered: advertising`;
- стоп-тема (спорт, шоу-бизнес, гороскопы, погода…) в заголовке или начале текста **и**
  нет экономических признаков → `filtered: off_topic`. Новость о продаже футбольного клуба
  за 12 млрд пройдёт: в ней много экономики, решать будет LLM;
- ни одной метки и ни одного «бизнес-слова» → `filtered: no_business_signal`.

Заодно префильтр **размечает статью правилами**: ключевые слова из
`config/taxonomy.yaml` дают метки макрофакторов и отраслей. Эта разметка используется,
если LLM недоступна, и сохраняется рядом с LLM-разметкой для сравнения.

### Шаг 5. Извлечение структуры LLM — `llm/classifier.py`, `llm/client.py`

Модель (по умолчанию **Qwen3.6 35B A3B** — `qwen/qwen3.6-35b-a3b` через API организаторов
`https://changellenge.up.railway.app/v1`, как в `interpreter/interpreter.py` команды)
получает **только текст публикации** (заголовок + тело, без источника, URL и даты)
и справочник меток («структура сведений о новости») и возвращает JSON строго по схеме
`schemas/extraction.py`:

```json
{
  "relevant": true,
  "summary": "ЦБ сохранил ключевую ставку 14% и ужесточил риторику",
  "facts": [
    {"text": "Ставка сохранена на уровне 14%", "confirmed": true},
    {"text": "Снижение ставки ожидается не раньше декабря", "confirmed": false}
  ],
  "numbers": [{"name": "ключевая ставка", "value": 14, "unit": "%"}],
  "entities": [{"name": "Банк России", "type": "regulator"}],
  "event_type": "regulator_decision",
  "macro_factors": ["key_rate", "inflation", "credit_market"],
  "industries": ["construction", "finance"],
  "regions": ["Россия"],
  "countries": [],
  "direction": "negative",
  "horizon": "short_term"
}
```

- `confirmed` отделяет факты от прогнозов и мнений. Это требование ТЗ: «отделяя
  подтверждённую информацию от предположений».
- Метки допускаются **только из справочника**: id, которые модель придумала сама,
  отбрасываются при валидации.
- Если ответ не прошёл валидацию, модели уходит **одна повторная попытка** с текстом
  ошибки. Если и она неудачна, статья размечается правилами (`rules_only`).
- `relevant: false` (модель решила, что новость не про бизнес) → статья фильтруется.
- Текст статьи передаётся модели в тегах `<article>` с явным указанием, что это данные,
  а не инструкции (защита от prompt injection).

### Шаг 6. Эмбеддинг — `core/embedder.py`

Векторизуется не сырой текст, а `заголовок + summary + ключевые факты`: так чище и
ближе к смыслу события. Модель локальная (fastembed/ONNX, без torch), по умолчанию
`paraphrase-multilingual-mpnet-base-v2` (768 измерений, хорошо работает с русским).
Токены LLM на эмбеддинги не тратятся.

Кроме вектора статьи целиком, текст режется на **чанки** (`parser/chunking.py`):
фрагменты по 2–4 предложения (~900 символов, не больше 12 на статью) по границам
предложений, у каждого свой вектор (таблица `article_chunks`). Именно чанки уходят агенту
как контекст: локальная LLM читает готовый текст и не ходит по URL. Статья и её чанки
векторизуются одним батчем.

### Шаг 7. Склейка в события — `parser/clustering.py`

Одну новость перепечатывают десятки СМИ разными словами, точный хеш это не ловит.
Новая статья сравнивается по косинусной близости с событиями за последние
`CLUSTER_WINDOW_HOURS` часов:

- близость ≥ `CLUSTER_SIMILARITY_THRESHOLD` → статья становится ещё одним источником
  события, метки объединяются;
- иначе создаётся новое событие.

**Событие — основная единица выдачи.** У него есть `n_sources` (сколько независимых
источников подтвердили новость) и «лицо»: заголовок и саммари статьи самого
доверенного источника.

### Шаг 8. Аналитика Альфа-Банка — `parser/analytics_loader.py`

PDF/TXT/MD из папки `ALFA_DOCS_PATH` загружаются при старте воркера, догружаются каждые
`REPROCESS_INTERVAL_MIN` минут и функцией `load_analytics()`. Для каждого документа:

1. **Текст страниц** — что найдётся первым:
   - текстовый слой PDF;
   - кеш прошлого распознавания `<имя>.analysis.json` рядом с файлом;
   - **Qwen3-VL** по картинкам страниц, если PDF сохранён картинками: модель переписывает текст,
     **описывает графики** (что показано, период, значения и тренд; значения «на глаз» помечены
     словом «около») и **переводит таблицы в Markdown** — например, таблицу прогнозов банка;
   - одноимённый `.txt` (например, распознанный на Mac) — если LLM недоступна.
2. **Чистка** (`parser/analytics_cleaner.py`): имена и контакты авторов, колонтитулы, номера
   страниц, юридические дисклеймеры — они портят векторы и подбор.
3. **Профиль документа через LLM** (`llm/doc_profiler.py`): название, дата, 3–6 главных тезисов
   банка (`summary`), общая позиция (`stance`: hawkish / dovish / neutral / risk), теги из
   справочника. Без LLM — правила по ключевым словам.
4. **Фрагменты** по границам предложений (~1200 символов) с номерами страниц; теги фрагмента =
   его собственные + теги документа; векторы фрагментов и документа.

Документы хранятся в `news.analytics_documents`, фрагменты — в `news.analytics_chunks`,
с `origin = "alfa_bank"`: в выдаче видно, где позиция банка, а где вывод модели (критерий 03).

**Кеш `<имя>.analysis.json`.** Распознавание и профиль стоят токенов (на 9 документах кейса:
~2.9 тыс. токенов на страницу для Qwen3-VL и ~9 тыс. на профиль документа), поэтому результат
сохраняется рядом с исходником и привязан к его sha256. Перезапуск, `load_analytics(force=True)`
и передача папки `data/alfa` вместе с `.analysis.json` другим членам команды — без новых затрат.
Папка монтируется в контейнер на запись именно ради этого.

**Если кончился дневной бюджет LLM**, недообработанные документы попадают в `errors`
и автоматически догружаются фоновой задачей, когда бюджет восстановится (сутки по UTC).
Загрузка защищена блокировкой в БД: воркер и ручной запуск не обрабатывают файлы одновременно.

### Фоновые задачи — `worker.py` + `scheduler.py`

Основной процесс контейнера — воркер (`python -m news_parser.worker`). Он запускается в
**одном экземпляре**: несколько воркеров запустили бы параллельные сборы.

| Задача | Когда |
|---|---|
| прогрев модели эмбеддингов, загрузка аналитики, первый сбор | через 2 с после старта |
| сбор со всех источников | каждые `COLLECT_INTERVAL_MIN` минут |
| дообработка статей `pending_llm` (не хватило бюджета или LLM лежала) | каждые `REPROCESS_INTERVAL_MIN` минут |
| нарезка на чанки статей, собранных до появления чанков (один раз, идемпотентно) | при старте |

## 3. Структура кода

Код разложен по слоям — по одному пакету на каждый блок схемы обработки. Каждый слой
знает только о слоях ниже себя, поэтому любой блок можно читать и менять отдельно.

```
      interface.py (функции)    cli.py · worker.py
                 \                    /
                  core/container.py  ← собирает слои вместе
       ┌──────────┬───────┴───────┬────────────┐
    parser/     llm/        filtering/      output/
 (сбор новостей) (Qwen)   (жёсткий фильтр)  (итоговый JSON)
       └──────────┴───────┬───────┴────────────┘
                     storage/  (БД)
                          │
              core/ (настройки, теги, эмбеддинги) · schemas/ (форматы данных)
```

| Слой | Отвечает за | Не делает |
|---|---|---|
| `parser/` | сбор из источников, очистка, префильтр, дедуп, чанки, склейка в события, загрузка аналитики | не решает, что показать клиенту |
| `llm/` | запросы к API модели и классификацию новости в теги | не ходит в БД |
| `storage/` | таблицы, подключение, **все** SQL-запросы | не содержит бизнес-логики |
| `filtering/` | клиент → теги и запросы, жёсткие правила, векторный поиск, подбор аналитики, (ранжирование) | не форматирует ответ |
| `output/` | сборка итогового JSON: пакеты `{client, news, analytics}`, `stance`, контекст для промпта | ничего не ищет, в БД ходит только за текстом статей |
| `interface.py` | публичные функции модуля (их зовут другие модули) | без логики — только вызывает слои и отдаёт JSON |

```
news-parser/
├── Dockerfile (собирается из корня репо), docker-entrypoint.sh, .env.example, pyproject.toml / uv.lock
├── alembic/                       # миграции БД
├── tests/                         # юнит-тесты (без БД и сети)
└── src/news_parser/
    ├── interface.py               # ПУБЛИЧНЫЕ ФУНКЦИИ: get_packets, match_client, ingest, stats, …
    ├── cli.py                     # те же функции из командной строки (вывод — JSON)
    ├── worker.py                  # процесс контейнера: фоновый сбор по расписанию
    ├── scheduler.py               # расписание задач воркера
    ├── config/                    # sources.yaml (источники), taxonomy.yaml (справочник тегов)
    │
    ├── core/                      # ОБЩЕЕ
    │   ├── settings.py            #   конфигурация из env
    │   ├── logs.py                #   логи в stdout
    │   ├── taxonomy.py            #   справочник тегов + разметка правилами по ключевым словам
    │   ├── embedder.py            #   модель эмбеддингов (одна на новости, аналитику и клиента)
    │   └── container.py           #   сборка зависимостей; Services.match = отбор → сборка ответа
    │
    ├── parser/                    # 1. ПАРСЕР
    │   ├── collectors/            #   источники: base (интерфейс), rss, cbr (курсы), moex (индексы)
    │   ├── fetcher.py             #   скачивание статьи (robots.txt, паузы)
    │   ├── cleaner.py             #   HTML → текст, нормализация, хеш для дедупа
    │   ├── prefilter.py           #   отсев мусора до LLM (только по тексту)
    │   ├── chunking.py            #   нарезка текста на чанки
    │   ├── clustering.py          #   склейка статей в события
    │   ├── pipeline.py            #   оркестрация: сбор → … → событие + чанки
    │   └── analytics_loader.py    #   загрузка PDF аналитики Альфа-Банка
    │
    ├── llm/                       # 2. LLM
    │   ├── client.py              #   запросы к API (Qwen), бюджет, журнал, список разрешённых моделей
    │   └── classifier.py          #   промпт, разбор и проверка JSON-разметки новости
    │
    ├── storage/                   # 3. РАБОТА С БД
    │   ├── db.py, models.py       #   подключение, таблицы
    │   ├── clients.py             #   чтение клиентов из companies / payments / person_company
    │   └── repository/            #   все запросы, по сущностям:
    │       ├── articles.py        #     статьи (дедуп по URL/хешу, очереди)
    │       ├── events.py          #     события (склейка, карточка, лента)
    │       ├── filters.py         #     SQL-сторона жёстких правил: теги → WHERE
    │       ├── chunks.py          #     векторный поиск по чанкам новостей
    │       ├── analytics.py       #     фрагменты аналитики
    │       ├── llm_usage.py       #     журнал вызовов LLM, дневной бюджет
    │       └── stats.py           #     статистика для stats()
    │
    ├── filtering/                 # 4. ЖЁСТКИЙ ФИЛЬТР + ВЕКТОРНЫЙ ПОИСК
    │   ├── profile.py             #   клиент → аспекты (теги + текст-запрос)
    │   ├── rules.py               #   аспект → обязательные теги новости
    │   ├── matcher.py             #   правила → вектор → аналитика к новости → Selection
    │   ├── candidate.py           #   отобранная новость со статьями и аналитикой
    │   └── ranking.py             #   ранжирование (пока заглушка)

    │   ├── packets.py             #   пакеты {client, news, analytics} для LLM-агента
```

## 4. Модель данных

Все таблицы в схеме `news` (`DB_SCHEMA`).

| Таблица | Что хранит |
|---|---|
| `events` | событие: заголовок, саммари, тип, направление, горизонт, метки (`macro_factors`, `industries`, `okved`, `regions`, `countries`), сущности, эмбеддинг, `n_sources`, `max_trust`, даты |
| `articles` | каждая статья, включая дубли и отфильтрованные (чтобы не качать повторно): текст, URL, источник, `status`, `extraction` (JSON выше), `extraction_meta` (как получена разметка), эмбеддинг, `event_id`, `cluster_similarity` |
| `article_chunks` | чанки статей (2–4 предложения) с эмбеддингом, `article_id`, `event_id` — контекст для агента |
| `analytics_chunks` | фрагменты аналитики Альфа-Банка: текст, документ, страницы, метки, эмбеддинг, `origin=alfa_bank` |
| `llm_calls` | журнал каждого обращения к LLM: модель, назначение, статья, токены, задержка, ошибка |

Индексы: GIN по массивам меток (быстрые фильтры `&&`), HNSW по эмбеддингам
(косинусная близость).

**Статусы статьи:**

| Статус | Значение |
|---|---|
| `extracted` | размечена LLM |
| `structured` | из ЦБ/биржи, разметка известна заранее |
| `rules_only` | размечена правилами (LLM не настроена или дважды вернула мусор) |
| `pending_llm` | размечена правилами временно, ждёт бюджета/LLM, будет дообработана |
| `duplicate` | точная копия другой статьи, привязана к её событию |
| `filtered` | отсеяна (причина в `status_reason`) |

**Трассируемость** (критерий успеха 12): по событию → его статьи (`get_event(id)`) →
по статье её текст, URL, метод разметки, id вызовов LLM и метки правил
(`get_article(id)`) → по id вызова запись в `llm_calls`.

## 5. Справочник меток (таксономия)

Файл `src/news_parser/config/taxonomy.yaml`, отдаётся целиком функцией `taxonomy()`.

- **`macro_factors`** (21 шт.): `key_rate`, `inflation`, `fx_rub`, `oil`, `gas`, `metals`,
  `gold`, `agri_commodities`, `gdp_growth`, `labor_market`, `consumer_demand`,
  `credit_market`, `bond_market`, `equity_market`, `taxes`, `customs_tariffs`,
  `sanctions`, `foreign_trade`, `budget_policy`, `regulation`, `logistics`.
- **`industries`** (24 шт.): у каждой отрасли есть список **двузначных кодов ОКВЭД-2**.
  Например, `construction` → `23, 41, 42, 43`. У события поле `okved` заполняется
  автоматически из его отраслей, так что клиента с `MAINOKVED_CODE = 41.20`
  можно матчить напрямую.
- **`event_types`** (13 шт.): `regulator_decision`, `macro_data`, `legislation`,
  `sanctions_trade`, `corporate_results`, `corporate_deal`, `default_bankruptcy`,
  `disruption`, `market_move`, `investment_project`, `management_change`,
  `geopolitics`, `other`.
- **`regions`**: субъекты РФ в именительном падеже («Москва», «Республика Татарстан»);
  `"Россия"` означает общероссийское событие.

Синтаксис ключевых слов: `"ключев ставк"` — основы слов, каждое ищется с начала слова;
`"re:газ(а|у|ом|е)?"` — регулярка целым словом. Второй вариант нужен для коротких основ:
иначе «газ» ловил бы «газету».

## 6. Как вызывать модуль: функции и CLI

HTTP-сервера нет. Есть два равноценных способа — один и тот же набор функций
(`src/news_parser/interface.py`), результат всегда готовый JSON (`dict` / `list`).

**Из Python** — если модуль агента работает в том же окружении (или импортирует пакет):

```python
from news_parser import get_packets, ClientNotFound

packets = get_packets("U_176", limit=5)          # [{client, news, analytics}, ...]
for p in packets:
    answer = interpret(p)                         # LLM-интерпретатор команды
```

**Из командной строки / другого контейнера** — те же функции, вывод JSON в stdout:

```bash

```

```python
from news_parser import search_events
hits = search_events(query="стоимость заёмного финансирования для застройщиков",
```

## 7. Единая модель эмбеддингов: подбор под профиль клиента

### Идея

Профиль клиента, чанки новостей и чанки аналитики Альфа-Банка векторизуются **одной
и той же моделью** (`EMBEDDING_MODEL`) и лежат в одном векторном пространстве, поэтому
их можно сравнивать между собой. Векторы разных моделей несовместимы, поэтому модуль
сам считает векторы и для запросов: снаружи их считать не нужно.

На выходе агент получает **не URL, а готовые куски текста**: саммари, факты с пометкой
«подтверждено / прогноз», чанки статей и чанки аналитики банка. Локальная LLM не умеет
ходить по ссылкам, ей это и не нужно. URL остаются в ответе только для пользователя
(«перейти к первоисточнику»).

### Почему профиль → аспекты, а не один вектор

Профиль — это таблица (коды, флаги, суммы), и модель эмбеддингов понимает её плохо:
«41.20» для неё просто цифры. А один усреднённый вектор теряет отдельные интересы
клиента. Поэтому `filtering/profile.py` раскладывает профиль на **аспекты**: у каждого
есть понятный текст-запрос (его и векторизуем), фильтры по меткам таксономии и вес.

Поля профиля совпадают с колонками таблицы `companies` из `schema.sql`, так что строку
из БД клиентских данных можно передавать как есть.

| Аспект | Из каких полей | Фильтры | Вес |
|---|---|---|---|
| `industry` — отрасль | `mainokved_code`, `mainokved_name` | отрасль таксономии + ОКВЭД | 1.0 |
| `financing` — стоимость заёмных денег | `has_loa`, `has_lea`, `has_gar`, `has_factoring` | `key_rate`, `credit_market` | 0.9 |
| `foreign_trade` — ВЭД | `fts_flag`, `fts_country_name` (данные ФТС) | `fx_rub`, `customs_tariffs`, `sanctions`, `foreign_trade`, `logistics` + страна | 0.9 |
| `liquidity` — доходность свободных денег | `has_dep` | `key_rate`, `bond_market` | 0.6 |
| `supplier_*` / `customer_*` — отрасли крупнейших контрагентов | `payments` (топ по сумме) | отрасль и ОКВЭД контрагента | 0.6 |
| `workforce` — персонал | `has_zpp` | `labor_market`, `taxes` | 0.5 |
| `region` — регион | `region` («г. Москва» → «Москва») | регион **и** хотя бы одна бизнес-метка у новости | 0.5 |
| `macro` — макрофон (у всех) | — | `inflation`, `gdp_growth`, `taxes`, `budget_policy` | 0.4 |

Отрасли контрагентов берутся только отличные от собственной, до двух на роль. Так
ловятся риски цепочки поставок: у перевозчика крупные поставщики — НПЗ и автозавод,
значит, важны новости о топливе и грузовиках.

ВЭД создаётся **только по данным ФТС** (`fts_flag`). Сигналы `fx_exposure` /
`import_dependency` из `data_loader` лишь меняют вес: они считаются эвристикой по первому
слову названия ОКВЭД («Деятельность…») и ложно ставят импорт почти всем клиентам.

Вес аспекта сейчас в отборе не участвует: он понадобится этапу ранжирования.

### Как считается выдача (`filtering/matcher.py`) — схема команды

```
Клиент ─┬─► теги (ОКВЭД, продукты → справочник taxonomy.yaml) ─► 1. ПРАВИЛА: жёсткий отсев по тегам
        └─► тексты-запросы аспектов ─► эмбеддинг ──────────────► 2. ВЕКТОРНЫЙ ПОИСК по новостям,
                                                                    прошедшим правила
                                        3. ВЕКТОРНЫЙ ПОИСК ПО АНАЛИТИКЕ: для каждой новости —
                                           по её вектору среди фрагментов с общими тегами
                                        4. РАНЖИРОВАНИЕ — пока не реализовано
```

1. **Правила.** Новость проходит, только если её теги совпали с тегами хотя бы одного
   аспекта клиента (по любому измерению аспекта: факторы, отрасли, ОКВЭД, регион, страна).
   Для региона нужна ещё и бизнес-метка. Новость без нужных тегов в выдачу не попадает
   ни при каком сходстве векторов.
2. **Векторный поиск** среди прошедших: чанки новостей сравниваются с векторами аспектов,
   чанки со сходством ниже `min_similarity` отбрасываются. Шаги 1 и 2 — один SQL-запрос:
   правила в `WHERE`, сходство в `ORDER BY`.
3. **Аналитика — в два шага.** Сначала **документы**: с общими с новостью тегами (жёсткое
   правило), не старше `ANALYTICS_MAX_AGE_DAYS` (730 дней; документ про сталь 2021 года
   отсекается), ближайшие по смыслу выжимки документа к новости — не больше
   `ANALYTICS_DOCS_PER_NEWS` (2). Потом **фрагменты только внутри выбранных документов**,
   ближайшие к вектору новости. Так фрагмент не «выпрыгивает» из документа на чужую тему.
   Общих тегов нет — аналитики нет: лучше пустой список, чем чужая аналитика.
4. **Ранжирование** пока не реализовано (`rank()` — заглушка): порядок новостей — сходство
   из векторного поиска. В ответе `meta.ranking = "not_implemented"`.

**Запасной поиск.** Если правила пропустили меньше `MATCH_MIN_NEWS` (3) новостей, выдача
добирается векторным поиском без правил с порогом выше на `MATCH_FALLBACK_MARGIN` (0.15).
Такие новости помечены `passed_rules: false` и стоят после прошедших правила.
`MATCH_FALLBACK=false` — строго только правила.

**Известное ограничение без ранжирования.** Общие темы (ставка, макро) почти всегда
ближе по вектору, чем узкие (отрасль клиента), поэтому верх выдачи у разных клиентов
с кредитами получается похожим. Персонализация при этом есть среди прошедших правила:
перевозчику проходят новости о топливе, ритейлеру — о маркетплейсах. Поднять их наверх —
задача ранжирования (веса аспектов, квоты на аспект, свежесть).

### Готовый контекст для промпта

Поле `context` — текст, который агент вставляет в промпт как есть. В нём три раздела:

- **Клиент**: описание компании словами и список её интересов (аспектов);
- **Новости**: для каждой `[N…]` дата, источники, тип, направление влияния, «почему
  отобрано», суть, факты с пометкой `[подтверждено]` / `[прогноз/мнение]`, фрагменты
  статей, ссылки на связанную аналитику;
- **Аналитика Альфа-Банка (позиция банка)**: `[A…]` с документом и страницами.

Внешние факты и позиция банка разведены по разным разделам, как требует ТЗ. Длина
ограничена `max_context_chars` (по умолчанию 12000) под маленькое окно локальной модели:
блоки добавляются по убыванию важности, около 65% бюджета уходит на новости, остальное —
на аналитику. Если что-то не поместилось, в конце контекста стоит пометка.

Если агенту удобнее собирать промпт самому, достаточно `render_context: false`
и брать структурированные поля.

### Трассируемость

По ответу восстанавливается, на чём основан каждый вывод: `N…` → `event_id` →
`get_event(id)` (все первоисточники) → `get_article(id)` (текст, метод разметки,
id вызовов LLM). `matched_aspects` + `aspects[].reason` показывают, **какие признаки
компании** привели к выбору новости (критерий 12).

### Пакеты для LLM (контракт команды) — `get_packets(client_id)`

Главная точка интеграции с LLM-модулем. Возвращает список пакетов — **по одному на
значимую для клиента новость**, каждый уходит в LLM отдельно:

```json
{
  "client": {"client_id": "U_176", "industry": "...", "revenue_rub": 18500000000, "region": "Москва",
             "products": {...}, "signals": {...}, "top_counterparties": [...],
             "linked_companies": [...], "people_regions": [...]},
  "news": {"news_id": 40, "url": "https://...", "title": "...", "published_at": "2026-10-21",
           "source": "Интерфакс", "text": "..."},
  "analytics": [{"chunk_id": "klyuchevaya_stavka_cb_rf::p2::c1", "doc_title": "...", "page": 2,
                 "text": "...", "stance": "hawkish", "doc_summary": "• ...", "doc_date": "2026-09-11"}]
}
```

Откуда что берётся (`output/packets.py`):

| Поле | Источник |
|---|---|
| `client` | **как есть** из `data_loader.get_client_info(client_id)`: библиотека модуля клиентских данных в корне репо |
| профиль для поиска | `companies` / `payments` / `person_company` напрямую: код ОКВЭД, ВЭД, отрасли поставщиков, покупателей и связанных компаний (в блоке `client` этого нет) + `client.signals` |
| `news.news_id` | id события (одна новость из нескольких СМИ = одно событие) |
| `news.url`, `source`, `published_at` | главная статья события (самый доверенный источник) |
| `news.text` | короткая статья — целиком; длинная — самые релевантные клиенту чанки по порядку, до `news_text_chars` (3000). LLM не нужно ходить по URL |
| `analytics` | 0–5 чанков, подобранных **к этой новости**: общие теги + ближайшие к вектору новости. Пусто, если общего с аналитикой банка нет |
| `analytics[].chunk_id` | `<документ латиницей>::p<страница>::c<номер чанка>` |
| `analytics[].stance` | позиция банка: `hawkish` / `dovish` / `neutral` / `risk` — из профиля документа (LLM); без профиля — правила по тексту фрагмента (`output/stance.py`) |
| `analytics[].doc_summary` | главные тезисы банка во всём документе (3–6 пунктов с цифрами) — общая позиция, а не только выбранный фрагмент |
| `analytics[].doc_date` | дата документа |

`signals` из `get_client_info` влияют на веса аспектов: `high` ×1.25, `low` ×0.7.
`credit_dependency` усиливает «стоимость заёмных денег», а `fx_exposure` / `import_dependency`
меняют вес аспекта ВЭД (сам аспект создаётся только по данным ФТС).

Параметры: `limit` (5 пакетов), `analytics_per_news` (3, максимум 5), `news_text_chars` (3000),
`window_days`, `min_similarity`, `trace=true`. С `trace` в пакет добавляется блок `trace`:
прошла ли новость правила, сходство, аспекты клиента и совпавшие теги, факты с `confirmed`,
сходство аналитики.
Без `trace` пакет строго соответствует контракту.

```python
from news_parser import get_packets
packets = get_packets("U_176", limit=5)          # trace=True — с объяснением отбора
```

```bash
docker compose exec news-parser python -m news_parser.cli packets U_176 --limit 5
```

Ошибки: клиента нет → `ClientNotFound`; нет библиотеки `data_loader` или её базы (например,
не обновлено материализованное представление `top_counterparties`) → `PacketsUnavailable` с причиной.

### Настройки

`MATCH_WINDOW_DAYS` (14), `MATCH_MIN_SIMILARITY` (0.3), `NEWS_CHUNK_CHARS` (900),
`NEWS_MAX_CHUNKS` (12).

База клиентских данных задаётся переменными `DB_HOST`, `DB_PORT`, `DB_USER`,
`DB_PASSWORD`, `DB_NAME`: их же читает `data_loader`, так что настройка одна на оба модуля.
Приоритет у news-parser: `PROFILES_DATABASE_URL` → `DB_*` → та же база, что `DATABASE_URL`.
Схема таблиц — `PROFILES_DB_SCHEMA` (`public`).

## 8. Бюджет токенов и работа без LLM

Общий ключ команды ограничен (в ТЗ: 500 ₽ в день), поэтому:

- В LLM попадает только то, что прошло дедуп и префильтр. В тестовом прогоне
  отсеивалось около 20–60% потока, в зависимости от источника.
- Статья обрезается до `LLM_MAX_INPUT_CHARS` символов: суть деловой новости почти
  всегда в начале.
- Перед каждым вызовом проверяется дневной лимит `LLM_DAILY_TOKEN_BUDGET` (сумма
  `llm_calls.total_tokens` за сутки UTC). Лимит исчерпан → статья размечается правилами
  со статусом `pending_llm` и **всё равно попадает в поиск**; когда бюджет появится,
  её доразметит фоновая задача.
- Аналитика Альфа-Банка размечается правилами, без LLM.
- `LLM_API_URL` пустой → модуль полностью работает на правилах. Удобно для разработки
  и как страховка, если API организаторов недоступен.

Расход видно в `stats()` (`llm_tokens_today`).

## 9. Безопасность

В ТЗ требуется описать механизмы безопасности AI-компонентов. В этом модуле:

| Механизм | Где |
|---|---|
| Нет сетевого интерфейса: у модуля нет HTTP-сервера и открытых портов, вызвать его можно только изнутри окружения (импорт или `docker compose exec`) | `interface.py`, `worker.py` |
| Журналирование каждого обращения к LLM (модель, токены, ошибка, статья) | `llm_calls`, `llm_client.py` |
| Лимит расходов LLM в сутки | `llm_client.py` |
| Защита от prompt injection: текст статьи передаётся как данные в `<article>`, модель предупреждена игнорировать инструкции внутри; ответ валидируется по схеме, метки — по белому списку | `extractor.py` |
| Модуль только читает внешние источники и пишет в свою схему БД; никаких действий во внешнем мире | архитектура |
| Уважение к robots.txt, пауза между запросами, честный User-Agent; антибот-защиту не обходим (поэтому banki.ru выключен) | `fetcher.py`, `sources.yaml` |
| Контейнер работает от непривилегированного пользователя | `Dockerfile` |
| Секреты только через переменные окружения, `.env` в `.gitignore` | `.env.example` |

Персональных данных клиентов модуль не получает и не хранит: профиль клиента живёт
у агента, сюда приходят только фильтры.

## 10. Развёртывание в Docker

### Требования

- **PostgreSQL 15+ с pgvector ≥ 0.5** (проще всего образ `pgvector/pgvector:pg16`).
- Пользователю БД нужны права `CREATE SCHEMA` и `CREATE EXTENSION`. Другой вариант:
  админ заранее выполняет `CREATE EXTENSION vector;` в этой базе.
- Исходящий интернет из контейнера (источники новостей, API LLM).
- Ресурсы: образ ~3.6 ГБ (модель эмбеддингов ~1.1 ГБ, библиотеки ~0.9 ГБ); RAM — около 1.5 ГБ (оценка, не замерялось).
- Сборщик любой: и BuildKit, и классический (`DOCKER_BUILDKIT=0`); плагин `buildx` не обязателен.

### Шаги

Всё — из **корня репозитория**: образ собирается оттуда, потому что ему нужны и
`news-parser/`, и библиотека `data_loader/`.

```bash
cp news-parser/.env.example news-parser/.env   # вписать LLM_API_KEY
docker compose up -d --build
```

Без compose (база уже есть отдельно):

```bash
docker build -f news-parser/Dockerfile -t news-parser .
```

```bash
docker run -d --name news-parser --env-file news-parser/.env -v "$(pwd)/data/alfa:/data/alfa:ro" news-parser
```

Что попадает в сборку, задаёт `.dockerignore` в корне — это белый список: код
`news-parser`, миграции и `data_loader`. Файлы `.env` с ключами, `.venv`, `data/` и `.git`
в образ не попадают.

При старте контейнер:

1. выполняет `alembic upgrade head`: создаёт схему, расширение `vector` и таблицы
   (повторный запуск ничего не ломает);
2. запускает воркер (`python -m news_parser.worker`) — фоновый сбор по расписанию.
   Портов нет: healthcheck Docker проверяет доступность БД командой `cli health`.

Через несколько секунд после старта загружается аналитика из `/data/alfa`
и проходит первый сбор. Проверка:

```bash
docker compose exec news-parser python -m news_parser.cli health
```

```bash
docker compose exec news-parser python -m news_parser.cli stats
```

Логи пишутся в stdout: `docker compose logs -f news-parser`.

### Библиотека data_loader внутри образа

`data_loader` лежит в корне репо. Образ собирается из корня, поэтому библиотека
просто копируется в `/app/data_loader` (`PYTHONPATH=/app`): отдельные контексты сборки
и плагин `buildx` не нужны.

Клиентские таблицы (`schema.sql`) должны существовать в базе `DB_*` и быть заполнены через
`data_loader.load_all_data(...)`, включая `REFRESH MATERIALIZED VIEW top_counterparties`:
без него `get_client_info` падает. В compose по умолчанию это та же база `db` (схема
`public`), а таблицы модуля новостей живут рядом, в схеме `news`.

### Важно про модель эмбеддингов

Модель скачивается **при сборке образа** (`ARG EMBEDDING_MODEL`), поэтому контейнер
стартует быстро и без доступа к HuggingFace. Чтобы сменить модель, нужно поменять
**одновременно** `EMBEDDING_MODEL` (в build-arg и в `.env`) и `EMBEDDING_DIM` (в `.env`) и
**пересоздать схему** `news`: размерность векторов зашивается в таблицы при первой
миграции.

```bash
docker build -f news-parser/Dockerfile --build-arg EMBEDDING_MODEL=intfloat/multilingual-e5-large -t news-parser .
```

## 13. Как расширять

- **Новый RSS-источник** — блок в `config/sources.yaml`, код не трогаем.
  Если в ленте только заголовки, ставим `headline_only: true` и маленький `min_text_chars`.
- **Новый тип источника** (Telegram, API, сайт без RSS) — класс в `parser/collectors/`
  с `type = "..."`, декоратором `@register` и методом `collect()`; плюс импорт
  в `parser/collectors/base.py: load_collectors`.
- **Новая отрасль или фактор** — блок в `config/taxonomy.yaml` (название, ключевые слова,
  для отрасли — коды ОКВЭД). LLM увидит его автоматически, он попадает в промпт из
  справочника. Старые события новой меткой задним числом не размечаются.
- **Другая LLM** — `LLM_MODEL` (любая из разрешённых, API тот же). Список разрешённых ID —
  `ALLOWED_MODELS` в `llm/client.py`. Рассуждения отключаются параметром
  `reasoning_effort=none` (`LLM_REASONING_EFFORT`); для модели без рассуждений его можно
  оставить пустым. Проверено на API кейса с Qwen3.6: ответ за 3–9 с, ~1.6–1.7 тыс. токенов
  на статью, валидный JSON с первой попытки.

## 14. Сценарий проверки

Команды — из корня репозитория: `docker compose exec news-parser python -m news_parser.cli <команда>`
(ниже — только сама команда). То же можно вызвать функциями из Python.

1. `health` → `{"status": "ok", "db": true}`.
2. Подождать первый сбор (1–2 минуты) → `stats`: статьи по источникам и статусам, `events > 0`,
   `llm_configured: true`.
3. `events --limit 10` — общая лента событий.
4. `search-events --query "ставка" --okved 41.20` — выдача меняется при смене `--okved`,
   `--region`, `--factor`; в `ranking.matched` видно, почему событие попало в выдачу.
5. `event ID` — факты с пометкой `confirmed`, список первоисточников с URL.
6. `article ID` — `extraction_meta.method` (`llm`/`rules`/`structured`) и `llm_call_ids`:
   происхождение разметки.
7. `ingest --title "…" --text "…"` — новость обрабатывается сразу и либо приклеивается
   к существующему событию, либо создаёт новое.
8. `analytics-search --query "ставка"` — фрагменты аналитики Альфа-Банка с документом и страницами.
9. `packets U_176 --trace` — пакеты для LLM в формате команды; в `trace` видно,
   почему отобрана каждая новость.
10. `match U_176` — новости и аналитика под клиента и готовый `context` для промпта.
    При смене клиента меняются аспекты и выдача.

## 15. Ограничения и что дальше

- **Источники с пейволлом или запретом скачивания** (Ведомости, ТАСС) работают по
  заголовку/анонсу. Сами по себе они малоинформативны, но подтверждают события из
  полных текстов.
- **Склейка в события** использует один порог близости; заголовки (headline-only)
  склеиваются с полными текстами хуже. Возможное улучшение — сравнивать заголовок
  с заголовком.
- **Аналитика** режется по предложениям, а не по смысловым разделам PDF; разметка
  правилами. Если появится запас бюджета, можно размечать фрагменты через LLM.
- **Telegram** не подключён намеренно: много шума и слабая трассируемость. Добавляется
  отдельным коллектором (публичное веб-превью `t.me/s/<канал>`) с низким `trust`.
- **Метрики качества** для мониторинга (критерий 08) модуль уже собирает в БД: доля
  `filtered` по источникам, доля `rules_only` и `pending_llm`, средний `n_sources`,
  ошибки и задержки LLM. Дашборд над ними пока не сделан.
